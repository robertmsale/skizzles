Approve ordinary local development commands when they run inside the workspace sandbox and do not mutate remote repositories, production services, credentials, or destructive filesystem state.

Treat reversible edits to local source files that implement authentication, authorization, session, permission, or other security behavior as ordinary workspace development; semantic subject matter alone does not make a source patch high-risk. Keep credential and secret values, signing material, external identity-provider configuration, permission grants outside source, token/session operations against live services, and production or shared auth state consequential and separately guarded.

Treat Flutter, Rust, Xcode, simulator, and browser dev-server commands as normal development work when they are local to the project. Re-running build tooling to recover from common Xcode or simulator sandbox/reinitialization errors is acceptable when the command does not delete user data, modify signing credentials, deploy, or touch production.

Treat ordinary local Git operations as acceptable when they are additive, repo-local, and consistent with the user's agent guidance. Allow Git status/diff/log/show/ls-files/rev-parse, branch creation or switching, staging, commits, and merges, including committing directly to main/master or merging another local branch into main/master. Allow conflict-resolution commands when they fix files in place and preserve the existing branch structure. Allow pushing a specific Git tag when the command clearly targets only that tag and does not push branches, broad refspecs, or `--tags`.

Allow pushing one explicitly named non-default branch to its verified configured remote when the user explicitly requested publishing the branch, creating or merging its pull request, or another workflow that necessarily requires that scoped push. Treat that current-task authorization as covering the necessary branch publication without a redundant approval turn. Keep pushes review-gated so the reviewer can verify the repository, remote, branch, payload scope, and user authorization.

Without explicit authority in the current task, require user confirmation or reject branch pushes, remote changes, branch or tag deletion, force-pushes, history rewrites, rebases, cherry-picks, stashes, resets, cleans, restores, checkout paths that could discard work, hook bypasses, and other non-additive Git surgery.

Explicit current-task user authority, relayed and confirmed by the root when another agent will execute it, may authorize one named serialized owner to perform a scoped rebase, cherry-pick, reset, exact-path restore, branch or ref deletion, or force-push. Do not require additive patch re-expression solely because the authorized operation changes history. Before approving or executing it, verify the exact repository and Git common-dir; the configured remote and fetch/push URLs when relevant; the exact named action, branch, ref, commit, and path scope; a clean worktree or explicit disposition for every local delta; exclusive integration ownership with no concurrent writer; that no unrelated, shared, or live-owner work will be discarded; and that source commits or refs are preserved or recoverable when applicable. Ensure the exact command remains within ordinary tool approval. For a force-push, require one exact non-default branch and prefer `--force-with-lease`. Afterward, verify final refs, status, and relevant remote URLs.

Covered shapes include resetting to one verified ref before a rebase; rebasing a detached checkout from a preserved published tip; cherry-picking one exact commit; restoring exact known unrelated paths during an uncommitted merge; deleting one exact integrated or deliberately abandoned branch; and force-pushing one exact non-default branch with lease protection. Each remains subject to the authority and verification requirements above.

For an uncommitted merge, an exact named-path restore to `HEAD` is permitted when explicitly authorized, status and diff are verified before and after, and the source objects and refs remain recoverable.

Authorization for one scoped operation is not blanket permission for broad refspecs, default or protected branches, globs or unknown paths, ambiguous cleanup, unrelated work, hook bypasses, credential changes, or production/publication actions beyond the exact grant. Keep Git actions high or critical if they could destroy unpushed work, publish private data, or mutate a remote/default branch outside the verified scope.

Approve deletion of an exact task-owned temporary path only after the command resolves a literal descendant of `/tmp` or another configured disposable runtime root, verifies the current task owns it and its release condition is satisfied, and avoids globs, shared roots, live resources, and unknown paths. Keep broad `/tmp` deletion and ambiguous cleanup review-gated.

Do not treat external infrastructure as production merely because it is remote or uses DNS. Approve bounded setup, repair, replacement, and cleanup of clearly non-production development, test, QA, preview, or staging resources when the user authorized the development or QA outcome that requires them. This includes scoped Cloudflare tunnels and DNS records with unambiguous non-production names such as `dev`, `test`, `qa`, `preview`, or `staging`. Task-level authorization for that outcome covers its necessary non-production infrastructure steps without requiring the user to repeat literal resource names. Require the command and target to be bounded, avoid customer traffic and production data, and prefer a documented rollback or cleanup path. Using an existing scoped credential for the authorized action is acceptable; creating, exposing, rotating, revoking, or broadening credentials is not implicitly authorized.

Reject production-impacting or ambiguously scoped actions unless the user explicitly requested the exact target and action in the current task. This includes production deployments and migrations, production or shared DNS and infrastructure changes, destructive cloud operations, credential mutation, and publishing releases. When a hostname or resource is not clearly non-production, or the action could redirect customer traffic, treat it as production rather than inferring safety.
